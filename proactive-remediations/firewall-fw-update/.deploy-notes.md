# .deploy-notes.md — firewall-fw-update PIA package

Internal-only design rationale and rollout plan. Not pushed to PIA.

## v1 scope

- SonicWall and Fortinet only.
- Posh-SSH is the transport.
- Vendor partials are stubbed to return plausible fake output so Pester can run without real hardware.

## Credential model (layered)

Resolution order lives in `private/credential-resolution.ps1`:

1. Per-probe SSH key file (`~/.cit/fw-ssh.key` or `-KeyPath`).
2. `PIA_FW_CREDENTIAL` env var (base64 `username:password`).
3. ITGlue fallback via `ITGLUE_API_TOKEN` + `ITGLUE_SUBDOMAIN` — **stubbed in v1**.
4. `NO_CREDENTIAL_SOURCE` abort JSON.

### ITGlue stub rationale

The ITGlue integration requires agreement on the flexible asset type (firewall password vs. configuration) and the exact query pattern (subdomain + API token). It is intentionally not implemented in v1 to avoid guessing at a credential storage design. The stub function throws a clear message directing the operator back to this file.

## PIA workflow design

Intended sequence:

1. PIA Agent runs `FW-Diag.ps1` on the probe device on schedule.
2. If `UpgradeNeeded = true`, PIA schedules `FW-Backup.ps1`.
3. On successful backup, PIA schedules `FW-StageFirmware.ps1` with the appropriate `ImagePath`.
4. On successful staging, PIA schedules `FW-ApplyUpdate.ps1`.
   - If the script returns `SCHEDULE_VIA_HALOPSA`, create a HaloPSA ticket/change request.
   - If it returns `NEEDS_CHANGE_WINDOW`, require explicit customer approval before retrying with `-AllowSingleUnitWithoutWindow`.
5. After apply, PIA schedules `FW-Verify.ps1`.
   - If `RECOVERY_NEEDED`, escalate to Tier 2 with the last diagnostic output.

## Schedule and safety

- `FW-Diag.ps1`: hourly or daily.
- All other activities: run on-demand from the PIA workflow; do not schedule independently.
- Maintenance window default is 06:00-22:00 local probe time. This assumes the probe is in the customer's time zone. If probes run UTC, add a `-TimeZoneOffset` parameter in v1.1.

## Pre-flight gates in `FW-ApplyUpdate.ps1`

- `-MaintenanceWindow` overrides the time check.
- `-BusinessHoursStart`/`-BusinessHoursEnd` customize the window.
- Single-unit firewalls abort with `NEEDS_CHANGE_WINDOW` unless `-AllowSingleUnitWithoutWindow` is passed.
- HA active units with a peer present are failed over before upgrade.

## Open questions before production

- Where are firmware images stored on each probe? The `ImagePath` parameter is passed explicitly, but a default repository path per site may be useful.
- Do SonicWall and Fortinet SSH sessions require a known-hosts policy? Posh-SSH default behavior may prompt; the PIA Agent runs non-interactively, so either accept-all or pre-seed host keys.
- Is the `~/.cit/fw-ssh.key` path correct for every probe deployment? Consider making this a PIA Agent environment variable instead.
- Should ITGlue lookup use a per-firewall serial number or the customer's ITGlue organization ID? Document before implementing.
- Do we want Posh-SSH installed machine-wide (`-Scope AllUsers`) for the SYSTEM context used by Intune PIA?

## Phase 2 (WatchGuard)

WatchGuard uses HTTPS REST on `https://<fw>:8080` with an API key. Windows PowerShell 5.1 lacks `-SkipCertificateCheck`, so either:

- Install the firewall's cert in the probe trusted store, or
- Gate the upgrade path to PowerShell 7+ where `-SkipCertificateCheck` is available.

Endpoints to implement:

- `GET /system/status`
- `POST /system/backup`
- `POST /firmware/upgrade`

## KPIs to track

- Backup success rate.
- Staging success rate.
- Apply initiation rate vs. schedule gate rate.
- Verify OK vs. recovery needed rate.
- Average time in maintenance window.
